# Canvas Dashboard 产品审视 · 2026-09-07

审视对象：本地 `main`，提交 `a93360f`。定位按“10 人以内共享部署、各自管理个人学业信息和日程”理解；目前不把多人编辑同一任务视为必备能力。

**总体判断：产品方向适合当前规模，网页主流程已有积累；Agent 接入尚未达到可以放心日常依赖的状态。** 当前最需要补的是数据正确性、授权后的可控性和真实接通体验。底层存储也存在实际实现与安全说明不一致的问题，不能因为其他模块迭代过多轮就跳过。

本次完成代码与部署配置审查、现有测试、隔离数据复现、Agent 页面桌面与手机浏览器验证。没有修改业务代码，没有访问真实账户内容，没有连接生产服务器或更改线上配置。因此，文中“已复现”指当前源码的隔离运行结果；生产资源、定时器和真实 MCP 客户端安装情况仍需另外核验。

**一、什么样的完整产品适合这个项目**

核心价值可以表述为：用户只需要看一个地方，就能知道接下来要做什么，而且能判断这份信息是否完整、是否最新、是否已经办妥。

建议围绕四个结果做验收：

- **不漏事**：未完成任务不会因为刷新、过期、来源差异或 Agent 的展示转换而消失。
- **不误改**：操作准确落在预期任务上，重试不会制造重复，误操作可以恢复。
- **知道可信度**：明确区分“确实没有事项”“尚未连接”“未同步成功”“正在显示旧缓存”。
- **普通成员能维护自己的接入**：能接通、能发现失效原因、能撤销单个客户端，遇到问题有可执行的下一步。

当前做得较好的基础包括：独立站点账户、正常路径下的数据隔离、平台原始缓存与本地状态分开、站点 Session 和 CSRF 防护、Agent 随机 Token 的哈希存储、加密备份与恢复工具、短时平台登录窗口，以及已有的前端回归测试。这些应继续保留。

对于 10 人以内的使用，单体 Flask 和轻量存储的维护成本合理。需要优先修复的是具体的数据事务和接口契约；没有必要立即引入微服务、复杂组织权限体系或分布式任务平台。

P1 表示应在把 Agent 当作可靠日常入口、或扩大使用前处理；P2 表示下一轮产品迭代处理；P3 表示按真实使用需求安排。以下优先级是本次产品判断，不是声称所有问题已经在生产造成事故。

**三、Agent 的关键问题与建议**

**A1. 有日期的项目会把整个待办查询拖垮。**

项目存储返回 `title`，Agent 汇总却读取 `item["name"]`。只要活动项目有截止日期，或包含带日期的未完成任务，就触发 `KeyError`。筛选在聚合之后执行，因此 `source=custom` 也不能规避。

复现结果：`source=all/custom/project` 三种查询均返回 500。现有 Agent 测试没有建立实际项目，所以没有发现。

建议复用已有统一事项转换，定义稳定的输出字段；按来源选择需要读取的数据。验收至少覆盖空项目、有日期项目、项目任务和单来源查询。

位置：[Agent 汇总](C:/DesktopFiles/canvas-dashboard/app.py:2474)、[项目事项真实结构](C:/DesktopFiles/canvas-dashboard/project_store.py:625)。

**A2. “标记完成”的任务定位不可靠。**

项目待办使用 `task-<project_id>-<task_id>`、项目截止事项使用 `due-<project_id>`。Agent 接口却尝试把整个 ID 转为整数，然后遍历所有项目寻找第一个同编号任务。任务编号只在单个项目内部唯一。

复现：两个项目都有任务 1；完成 `task-2-1` 返回 404；改传 `1` 返回成功，但被完成的是项目 1 的任务，项目 2 的目标任务未变。项目截止事项也没有相应的完成处理。平台事项则没有检查 ID 是否存在：对不存在的 Canvas ID `99999` 仍返回 `completed=true`。

建议使用明确的来源、实体类型和完整复合 ID；精确定位后才写入，回传实际修改的任务及最终状态。项目整体完成与单个任务完成必须区分。完成平台事项的结果应明确为“在工作台中标记完成”，目前不会替用户向学校平台提交作业。

位置：[Agent 完成逻辑](C:/DesktopFiles/canvas-dashboard/app.py:2505)、[项目任务 ID](C:/DesktopFiles/canvas-dashboard/project_store.py:651)。

**A3. 普通待办编号复用和缺少幂等保护，会放大 Agent 重试风险。**

自定义待办按“现存最大 ID＋1”分配编号。删除最大的那条、或完成事项经过自动清理后，编号可以重新分配。浏览器缓存的旧操作和 Agent 对话中记住的旧 ID 因此不再稳定。

复现：删除任务 1 后，新建的不同任务再次获得 ID 1；执行旧任务的完成请求，新任务被标记完成。相同新增请求带同一个 `Idempotency-Key` 连续发送两次，仍产生两条事项。

建议先使用不会复用的持久编号或 UUID，再给新增写操作提供客户端请求 ID 去重；必要时给修改操作加版本检查。让完成操作支持恢复未完成，并提供近期操作记录。这比增加每次操作的弹窗更能解决误操作。

位置：[ID 分配](C:/DesktopFiles/canvas-dashboard/app.py:2637)、[自动清理](C:/DesktopFiles/canvas-dashboard/app.py:437)。

**A4. 配置包的服务地址可能把 Token 发到 HTTP。**

nginx 以 HTTPS 对外服务，并通过 HTTP 访问 Waitress，同时发送 `X-Forwarded-Proto: https`。Flask 没有对应的代理处理；下载包和 Skill 客户端默认地址使用 `request.host_url`。

按该代理方式模拟请求，下载包实际生成 `http://canvas-dashboard.xyz`。MCP 客户端允许这个地址，并直接携带 `Authorization` 发请求；服务器稍后跳转到 HTTPS，不能保护已经通过 HTTP 发出的首次请求。网页上的预览使用浏览器 `location.origin`，所以预览与下载包还可能不同。

建议使用明确配置的 HTTPS 公网地址，或仅信任已知反向代理层数来恢复外部协议。客户端应拒绝非回环 HTTP 地址，并限制跨源重定向。另用标准库重定向处理器验证了 Authorization 会被保留到跨源重定向请求，属于附加的凭据外传风险。

位置：[MCP 包地址](C:/DesktopFiles/canvas-dashboard/app.py:2259)、[Skill 包地址](C:/DesktopFiles/canvas-dashboard/app.py:2318)、[客户端请求](C:/DesktopFiles/canvas-dashboard/agent_mcp.py:148)。代理处理依据见 [Flask 官方说明](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/)，重定向头行为见 [Python 官方说明](https://docs.python.org/3/library/urllib.request.html#urllib.request.Request.add_header)。这是对当前源码和仓库部署配置的验证，未下载生产账户的实际配置包。

**A5. 同步状态工具不可用，数据新鲜度也没有贯穿 Agent 查询。**

`/api/agent/v1/sync/status` 调用 `platform_sync.all_platform_sync_statuses()`，模块中没有这个函数，实际返回 500。即使只修复该调用，MCP 格式化还使用 `last_sync_at`；当前元数据实际使用 `last_success_at` 和 `last_attempt_at`，字段仍需对齐。

更深层的问题是：Agent 的清单直接读缓存。Canvas、好课、智学盟的现有刷新依赖网页/API 访问；Agent 清单不会触发这些刷新。长期只用 Agent，不能假定缓存会自动变新。其输出也没有 `last_success_at`、`stale`、失败的平台清单等信息，“没有待办”与“没有可用数据”容易混淆。

建议每次汇总都附带各来源的最后成功时间、数据状态和覆盖范围；Agent 回答应保留这些信息。需要更新时可以发起受限后台刷新，并明确返回“正在更新、当前结果截至何时”。对于仅用 Agent 的成员，应有可独立运行的同步路径。

位置：[错误调用](C:/DesktopFiles/canvas-dashboard/app.py:2695)、[MCP 字段](C:/DesktopFiles/canvas-dashboard/agent_mcp.py:315)、[当前元数据](C:/DesktopFiles/canvas-dashboard/platform_sync.py:26)、[网页刷新定时器](C:/DesktopFiles/canvas-dashboard/frontend/templates/index.html:3493)。

**A6. 日程和任务查询范围不一致。**

指定日期接口只读取课程与排程事项，没有像今日接口一样补充自定义待办、平台作业和项目截止事项。`get_todos` 也没有输出自定义子任务。项目汇总使用的 `todo_items()` 本身只包含活动项目中带日期的未完成事项，因此声称 `status=completed/all` 覆盖项目历史并不成立。

复现：同一天有父任务、带日期子任务；今日接口能看到二者，指定同一天的日期接口返回空截止列表；待办清单中子任务缺失。查询参数还没有服务端枚举校验，错误来源可能返回空清单，错误状态可能退化为全部。

建议今日与指定日期复用同一查询；清楚区分“完整任务列表”和“进入日程的带日期事项”。统一输出日期、精确时间、时区、全天标记和可执行操作。当前新增只支持日期，不能兑现示例中“明天晚上截止”的精确时间含义。

位置：[指定日期接口](C:/DesktopFiles/canvas-dashboard/app.py:2595)、[自定义任务转换](C:/DesktopFiles/canvas-dashboard/app.py:2423)、[MCP 新增参数](C:/DesktopFiles/canvas-dashboard/agent_mcp.py:83)。

**A7. 主项目和 Next Action 在接口转换中丢失。**

存储字段为 `main_project_id`，Agent 返回 `state.get("primary_project_id")`，结果一直为空。`load_projects()` 返回任务列表与 `is_next_action`，MCP 却寻找每个项目上已经计算好的 `next_action`，没有调用现有 `overview()`。

复现中实际主项目为项目 2，API 返回 `primary_project_id=null`，MCP 只显示项目名称与日期，没有主项目标识及下一步任务。REST 原始任务数据仍在，但模型从 MCP 工具无法得到它们。

建议复用项目概览，保留项目状态、任务标识、主项目和下一步行动。结构化结果应保留原始字段，再附便于阅读的摘要。

**A8. 认证的异常路径没有正确关闭。**

正常测试中，Alice 的 Token 不会让 Bob 读到 Alice 的待办，Token 撤销也正常。但账户检查只拒绝“账户存在且不活跃”，没有拒绝“账户不存在”。

模拟账户表中删除 Alice、但用户目录及 Token 因清理失败而残留，旧 Token 仍能通过 `/ping`。这不是声称正常的成功删除一定会遗留文件；问题是异常清理路径没有第二道认证约束。`auth.delete_account()` 本身忽略目录删除错误，使这种边界值得修复。Token 文件也没有绑定不可复用的 `account_id`。

另外，每次认证扫描其他用户的 Token 文件。先遇到损坏文件会直接抛出异常；复现中 Alice 的 Token 文件损坏后，Bob 的有效 Token 也得到 503。

建议要求账户确实存在、状态为 active，并将 Token 绑定账户不可变身份。凭据应能定位到自己的记录，单用户坏文件仅影响该用户；不要把错误数据改为空来绕过失败。

位置：[账户状态检查](C:/DesktopFiles/canvas-dashboard/agent_auth.py:99)、[全用户扫描](C:/DesktopFiles/canvas-dashboard/agent_auth.py:84)、[删除账户](C:/DesktopFiles/canvas-dashboard/auth.py:250)。

**A9. 权限和追溯能力适合做轻量补齐。**

当前每个用户只有一个长期有效 Token，所有接入客户端共用，读和写无法分开。服务端记录最后使用时间，但没有逐次操作的来源、目标、结果和恢复入口；页面也未展示最后使用时间。密码重置后，原 Agent Token 仍有效，复现为 200。

独立于站点密码的 Token 生命周期可以是合理设计，但账户恢复流程需要明确“是否同时撤销外部访问”；否则用户会误以为重置密码已经收回全部访问权。

建议最低限度支持：客户端名称、只读/可写、单独撤销、可选到期、最近使用、近期写操作与撤销。先提供只读授权，用户按需开启写入即可，不必为这个规模立即建设 OAuth 平台。外部课程标题、事项文本应作为数据处理；可疑文字不能自动变成新的操作指令。服务端权限检查仍是实际授权边界，工具描述和模型提示不能替代它。

位置：[Token 文件结构](C:/DesktopFiles/canvas-dashboard/agent_auth.py:25)、[认证装饰器](C:/DesktopFiles/canvas-dashboard/app.py:2207)、[页面授权说明](C:/DesktopFiles/canvas-dashboard/frontend/templates/dashboard/_placeholder_views.html:594)。

**A10. MCP/Skill 的“开箱即用”承诺需要端到端验证。**

下载包的 Claude 配置只写相对路径 `canvas_mcp.py`，说明让用户把脚本放到固定路径，却没有要求把配置里的参数改成该绝对路径。客户端若从另一个工作目录启动就找不到脚本。Cursor 包又把 `python canvas_mcp.py` 合成一个 command，和网页预览的 command/args 分开格式不一致；需要选定实际支持的客户端逐一验证，不能由压缩包存在推断兼容。

stdio 子进程复现发现：UTF-8 环境可以读取工具列表；设置为 GBK 时，输出不能按 UTF-8 JSON 解析。脚本没有固定标准输入输出编码。传入非对象 JSON `[]` 会使服务退出；调用未知工具返回 `isError=false`。部分异常已能返回 `isError=true`，但并非完整统一的错误契约。

建议提供 Python 版本/可执行路径检查、绝对脚本路径、明确的 UTF-8 设置、`ping` 自检和分阶段安装说明；工具参数在服务端校验，错误使用机器可辨认的错误结果。Skill 示例客户端还没有请求超时，应一并补齐。当前 8 个工具与页面“7 个工具”的说明也需一致。

MCP 明确要求消息使用 UTF-8，并区分协议错误与工具执行错误，见 [传输规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) 与 [工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)。旧协议版本号本身不足以证明客户端不兼容，本次不把它单独列为已确认故障。

位置：[下载包配置](C:/DesktopFiles/canvas-dashboard/app.py:2261)、[stdio 循环](C:/DesktopFiles/canvas-dashboard/agent_mcp.py:322)、[Skill 请求](C:/DesktopFiles/canvas-dashboard/app.py:2382)。

**A11. Token 管理页面的交互状态需要修正。**

重新生成的确认条件依赖 placeholder 是否包含“已生成”，但首次生成没有更新这个 placeholder。浏览器复现：第一次生成后，再次点击“重新生成”没有任何确认就更换 Token。当前页面宣称离开后隐藏完整密钥，实际侧栏切换只是隐藏 DOM，切回后明文和配置仍在。

桌面 1440px 与手机 390px 下没有发现横向溢出，页面也没有 JS 运行错误。更主要的体验缺口是用户只有“Token 已激活”，看不到“哪个客户端已经连通、最近一次调用是否成功”。手机页面大量安装说明和完整 JSON 占据长页面，但缺少连接完成反馈。

建议以显式 `has_token` 状态管理操作，落实离开时的清理承诺；加入“下载/配置/首次连接成功”三个明确步骤。配置错误、Token 错误、网络错误和服务端故障给出不同处理建议。

**四、Agent 以外的稳定性和产品问题**

**S1. 当前存储缺少文档承诺的原子写入，而且进程间有真实共享写入。**

`storage.write_json_file()` 使用 `Path.write_text()` 直接覆盖目标文件，没有临时文件、`fsync` 或 `os.replace`。模拟磁盘写入中途失败，原 JSON 被截断，原值没有保留。损坏后会停止读写并保留损坏副本，这个机制是有的，但它不能还原本次覆盖前的正确文件。

`threading.RLock` 只能协调同一进程。现在已经有网页进程和智慧树 worker 同时更新同一份 `platform_sync_status.json`，不是等将来加多进程网站才有问题。双进程复现中，两个进程均先读取旧值再更新，最终只保留后写入的那一方。

建议先恢复原子替换，并对跨进程共享的读改写使用跨进程锁或 SQLite 事务。两者解决的问题不同：原子替换防半份文件，事务/锁防更新覆盖。更新文档，使其准确反映最终实现，再增加中途写入失败和双进程更新的验收用例。

位置：[写入函数](C:/DesktopFiles/canvas-dashboard/storage.py:57)、[进程内锁](C:/DesktopFiles/canvas-dashboard/storage.py:30)、[网页写同步元数据](C:/DesktopFiles/canvas-dashboard/app.py:857)、[worker 写同步元数据](C:/DesktopFiles/canvas-dashboard/zhihuishu_worker.py:120)。

**S2. 过期事项的产品语义需要统一。**

Canvas iCal 解析直接过滤早于今天的事项。一个仍存在于订阅源、没有被本地标记完成的任务，会在日期过去之后从刷新结果消失。另一方面，今日视图复用日历导出筛选，已经过了当天截止时刻的平台事项也不显示；中午查询时，上午 10 点到期的未完成事项就不在今日列表中。

这使“未完成”“逾期”“不再展示”混在一起。对于防止漏交作业的产品，建议把逾期与完成分开；逾期保留到用户处理，或用明确可配置的归档期限。历史完成记录也应有可查的去处，避免只靠备份回忆完成过什么。自定义事项目前存在读取列表时自动删除已过保留期完成任务的行为，应在产品中说明。

位置：[Canvas 过滤](C:/DesktopFiles/canvas-dashboard/canvas_auth.py:207)、[今日视图所用筛选](C:/DesktopFiles/canvas-dashboard/app.py:510)、[完成事项清理](C:/DesktopFiles/canvas-dashboard/app.py:437)。

**S3. 小团体的用户上限目前只是使用预期。**

注册入口公开，没有邀请码或成员名单。注册限流的 key 包含用户名，换一个用户名就进入另一个计数桶。复现同一来源连续注册 7 个不同用户名，全部成功，超过了代码中看起来像“5 次”的注册限制。

建议提供关闭公开注册、一次性邀请码或管理员创建账号中的一种简洁机制，并补充按 IP 总量、账户总量和昂贵登录窗口的资源限制。Agent 路由也没有独立限流；错误循环和频繁轮询应有可辨识的 429 和退避提示。

位置：[注册限流](C:/DesktopFiles/canvas-dashboard/app.py:658)、[限流键](C:/DesktopFiles/canvas-dashboard/app.py:220)。

**S4. 上游慢请求仍可能拖慢整个工作台。**

Waitress 只有 4 个线程；Canvas 请求直接等外部网络，超时 30 秒。好课首次无缓存、智学盟同步和部分登录确认也有同步等待路径。少数成员同时打开或刷新，就可能用满线程；这时读本地缓存的 Agent 请求和健康检查也需要排队。

这属于从调用链推导的资源竞争风险，本次没有对生产压测。建议把平台读取统一为缓存优先、后台刷新，限制同一用户和全局刷新并发；再用隔离的慢上游场景测端到端响应。仅增大线程数不能替代超时预算、缓存与队列控制。

位置：[Waitress 线程数](C:/DesktopFiles/canvas-dashboard/serve.py:72)、[Canvas 同步请求](C:/DesktopFiles/canvas-dashboard/canvas_auth.py:152)、[好课首次加载](C:/DesktopFiles/canvas-dashboard/app.py:927)。

**S5. 日程时间、学期和调课规则仍需作为核心数据验收。**

时间字段只检查 `HH:MM` 形式及字符串顺序，`24:61` 到 `25:99` 的一次性日程能成功写入。建议用真实时间解析，并校验日期、时间区间、重复范围与单次跳过规则。

当前课程缓存虽然保存自己的 `semester_start`，今日课程计算却接收外部当前学期起点。Agent 指定日期接口也调用当前的 `get_term_info()`，没有按目标日期选择学期。查询跨学期日期时，课程标签、周次与起点可能不一致；旧课表也缺少换学期时的显式更新要求。节假日信息主要是展示信息，不能由此推断课程已经按校历停课或调休。

建议把课程明确绑定学期，对跨学期查询说明数据范围，并支持必要的单次停课/补课覆盖。对当前小团体，先保证周次、单双周、日期范围、冲突提示和历史日期一致，不必立即实现复杂排课优化。

位置：[时间校验](C:/DesktopFiles/canvas-dashboard/app.py:1430)、[课程展开](C:/DesktopFiles/canvas-dashboard/schedule_store.py:92)、[Agent 日期查询](C:/DesktopFiles/canvas-dashboard/app.py:2599)。

**S6. 恢复能力已有基础，但运行健康和数据健康还需要分开。**

现有加密备份往返测试通过，也有恢复演练和版本回滚脚本。但 `/healthz` 即使知道最后成功同步很久以前，也没有用陈旧时间判定 worker 异常；旧进程锁文件存在同样不能证明进程正在运行。一个长期停更的数据源可能仍然返回健康。

建议明确三类状态：网页是否可用、平台数据是否及时、备份是否可恢复。小团体至少应能让维护者看到最近备份成功/恢复演练、各平台最久未同步账户和近期重复错误。告警只在持续异常或需要处理时触发，避免每次轮询都通知。

备份本身包含持久用户 JSON，Agent Token 哈希也随之回到备份时的版本。仅撤销 Token 后再恢复旧备份，旧凭据有重新生效的可能；需要将“恢复后轮换外部凭据”或“备份外的撤销版本”纳入恢复流程。该项为文件纳入规则与认证逻辑的静态推论，未恢复生产备份验证。

位置：[worker 健康判定](C:/DesktopFiles/canvas-dashboard/app.py:121)、[备份与恢复说明](C:/DesktopFiles/canvas-dashboard/docs/backup-and-restore.md)。

**五、用户体验与功能边界的下一步**

| 用户场景 | 当前产品的主要缺口 | 适合下一轮的改进 |
| --- | --- | --- |
| 新成员第一次使用 | 要理解多个平台、课表导入和 Agent 的不同接法 | 以“连接一个平台→看到第一条事项→确认同步→可选接入 Agent”为首次使用路径 |
| 问“今天还有什么事” | 过期、子任务、课程、项目的范围不一致 | 一个统一日期查询，同时展示今天与尚未处理的逾期事项 |
| Agent 返回“没有待办” | 可能只是没有缓存，或来源数据不完整 | 显示覆盖来源、最后成功时间、未连接/失败来源 |
| 用 Agent 新增后查看网页 | 自定义待办没有和平台一样的定时刷新，也没有变更推送 | 页面重新获得焦点时轻量检查变更，或提供“有新变化”提示 |
| Agent 做错一次 | 缺少写入来源、历史和 Agent 内恢复操作 | 近期操作列表、恢复未完成、请求去重；避免靠重复确认弥补 |
| 手机接入 Agent | 配置代码与安装信息较长，缺少成功检测 | 按客户端展示必要步骤和自检，折叠高级选项 |
| 用户忘记密码 | 已有离线重置工具，但登录页没有“如何恢复”的入口 | 给出恢复路径或联系维护者入口；暂不必建设邮件服务 |
| 防止错过截止时间 | 有日历订阅，但不能据此承诺准点主动提醒 | 明确订阅刷新和提醒边界；先打通一种可靠提醒渠道，并可检查状态 |
| 用户想退出或保存自己的数据 | 有管理员级备份，缺少用户级日程/项目导出入口 | 提供个人 JSON/CSV/ICS 导出，和账户删除前的数据获取路径 |

另外，字体依赖 Google Fonts；建议为学校网络和移动网络准备稳定的本地字体/回退策略。手机实测没有出现横向滚动，但字体可达性、真实成员的任务完成时间和首次接入成功率没有在本次做用户研究，不把界面审查当作这些指标的证明。

“小团体”目前可以继续表示多人分别拥有个人工作台。如果以后确有共享实验、共同项目、互相分工的需求，再增加明确授权的共享空间、负责人和变更通知；避免提前把个人日程做成默认公开的团队数据。

**六、建议的落地顺序与验收**

| 阶段 | 范围 | 结束条件 |
| --- | --- | --- |
| 第一轮：修复可靠性 | 原子存储与跨进程更新、完整任务 ID、ID 不复用、Agent 项目/状态错误、HTTPS 地址、认证异常边界 | 写失败保住旧数据；并发不丢更新；Agent 操作准确；下载配置不携带明文网络风险 |
| 第二轮：完成 Agent 产品闭环 | 统一查询、数据新鲜度、客户端配置与自检、只读/可写授权、调用记录、重试和恢复 | 从下载到实际客户端查询/新增/完成/撤销形成完整流程，结果与网页一致 |
| 第三轮：适合成员日常使用 | 邀请准入、逾期与历史、换学期、个人导出、恢复指引和必要告警 | 维护者不在线时成员仍能判断状态、找回接入并保存自己的信息 |
| 扩大规模时 | 根据响应时间、刷新积压和用户量决定数据库与 worker 并发策略 | 使用测量结果决定扩容；保持用户隔离和平台限流 |

推荐把下列实际场景作为下一次 Agent 发布验收，而不是只检查接口返回 200：

1. 全新成员没有连接平台时，Agent 能说明未连接，而不声称“全部做完”。
2. 同时存在四个平台、自定义子任务、两个任务同编号的项目时，列表完整且能准确操作目标。
3. 今日和指定同一天的查询，在事项范围上保持一致；临近截止、刚过期和跨学期日期有明确行为。
4. 网页改名、删除、完成与 Agent 重试并发发生，不误改、不重复、不丢失其他修改。
5. 模拟失效凭据、损坏单用户文件、慢上游和 worker 停止，其他用户仍可访问，回答能说明数据状态。
6. 下载的配置从不同工作目录启动，使用至少一个真实目标 MCP 客户端完成接通，Windows 中文环境也能正常通信。
7. 撤销单个 Agent、重置密码、删除账户、恢复备份后的外部访问，均符合产品明确公布的规则。
