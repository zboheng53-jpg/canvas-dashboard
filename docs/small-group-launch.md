# 小范围开放：容量、维护与发布判断

这是 2026-09-28 的发布前评估。网站定位是供一小群同学各自使用的个人工作台；目前没有团队共享任务、成员权限或协作编辑。

## 先把「人数」分清

注册账户数、同时打开网页的人数、同时发起同步的人数、同时运行浏览器登录窗口的人数，是四个不同的容量指标。不能从 8 个 Waitress 线程推导「最多 8 人」；空闲页面几乎不占请求线程，慢上游请求却可能独占线程几十秒。线程用完后会排队，见 [Waitress 的请求调度说明](https://docs.pylonsproject.org/projects/waitress/en/latest/design.html)。

本次只读检查生产机器：2 vCPU、1967 MiB 内存；当时可用 1181 MiB，swap 使用 1019 / 1987 MiB，根分区使用 73%、剩余约 14 GiB。Web 服务约 27 MiB，智慧树 worker 的 systemd cgroup 约 658 MiB。以上是瞬时读数，不代表峰值或每用户增量；已有 swap 不足以单独判定正在内存抖动。

**建议第一批邀请 10–20 个账户，分散完成首次平台登录。** 这是运营批次建议，不是压测证明的上限。目前没有生产同配置、带真实同步和浏览器登录的压力测试，不能承诺最大并发人数。达到一两百注册账户前也未必需要数据库；真实瓶颈更可能先出现在浏览器内存、慢平台请求和个人维护时间。

本次加入 `scripts/benchmark_workspace.py`：只在本机临时目录生成假账户，用单进程、8 线程 Waitress 测试待办、项目、统一事项与议程读取。默认每账户 30 条待办、5 个项目行动，1/5/10/20 个并发客户端，每个客户端连续读四个端点三轮。它不会向生产或教学平台发请求。运行：

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_workspace.py --output test-results/capacity.json
```

本机结果只证明这类请求可以并发运行，不能换算为线上支持多少人；也未覆盖网络、TLS、注册密码哈希、首次同步、后台浏览器与备份争用。

2026-09-28 本机执行共 432 次请求、0 失败；1 / 5 / 10 / 20 个并发客户端的 p95 分别为 43 / 91 / 202 / 448 ms。20 客户端约 76 请求/秒。运行时另有浏览器回归负载，因此这是一份功能性容量探测，不是独占机器的性能基线；原始记录位于本次本地 `test-results/release-work/capacity.json`。

## 这轮先加的保护

第一批整改的当前实现与人工检查方法见 [运维说明](operations.md#basic-operational-monitoring)：五个普通 HTTP 平台共用 2 线程／32 任务预算，普通读取缓存优先，账户独占锁仅保护关键写入；Nginx 直读静态资源并剥离 VNC 下游认证头。旧密码课表入口已在代码中关闭；废弃应用的停服归档在部署成功后执行。这些是待验收的实现状态，尚不能代替实际发布、真实平台登录或生产峰值资源证据。

- 智慧树和同济课表认证窗口共用 `CANVAS_DASHBOARD_LOGIN_MAX_SESSIONS`，默认总共 1 个；并发启动直接返回 429 和可重试提示，不占着请求线程排队。每个容器已有 512 MiB、0.5 CPU 和进程数限制。内存限额不等于内存预留，swap 的行为也须单独理解，见 [Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)。
- `CANVAS_DASHBOARD_REGISTRATION_ENABLED=0` 可以临时关闭新注册；已有用户正常登录。修改服务环境后重启生效，默认仍允许注册。
- Canvas 馈送源默认只允许 `canvas.tongji.edu.cn`。其他学校由维护者在 `CANVAS_DASHBOARD_CANVAS_FEED_HOSTS` 中用逗号加入核验过的域名；只允许 HTTPS 443，不跟随重定向，不把带 Token 的 URL 写入错误日志。它是受信上游白名单，不能添加用户任意控制的域名。
- 原有账户隔离、会话撤销、请求限速、加密备份、损坏 JSON 停止写入和部署回滚继续保留；没有迁移真实数据。

## 开放后会多出来的工作

| 实际麻烦 | 提前约定 |
| --- | --- |
| 同学忘记密码、换设备、登录失效 | 忘记站点密码由维护者核实身份并签发一次性重置凭据；第三方登录失效需本人重新认证。不要让同学发密码给你。 |
| 同一校园网集中注册被限流 | 现有注册限制是同一出口 IP 每 30 分钟最多 5 次尝试，成功和失败都计入。首次邀请应分批完成，遇到 429 按等待时间重试；不要为了现场演示关闭全部限流。 |
| 「平台上有，但这里没有」 | 收集平台名、操作时间、步骤、最近成功同步时间；先区分缓存过期、已隐藏、本地完成和上游改版。反馈截图遮住身份、Token、订阅链接。 |
| 误以为勾选等于交作业 | 指南和展示页明确本地操作不会提交到教学平台；原平台是截止与提交状态的最终依据。 |
| 不同账号触发此前没测过的情况 | 关注无课程、多课程、未选学期、同名作业、不同认证方式、手机浏览器；发现后用脱敏样例补回归，不复制同学凭据。 |
| 半夜上游改版或服务器故障 | 给出清楚的缓存与失败状态；定一个自己能承担的处理节奏，不承诺全天即时恢复。平台故障不应阻断自定义待办。 |
| 删除和备份恢复争议 | 删除是永久操作；恢复前停止写入并遵守删除账本。首次开放前的发布仍跑现有备份与隔离恢复演练。 |
| 内容和凭据托管的责任 | 公开说明存储内容、用途与删除入口。服务端加密依然意味着服务器密钥持有人能解密，不能宣传端到端加密或“维护者看不到”。 |
| 更新影响所有同学 | 先预览验收，再发布；有影响的行为改动记录在更新日志。保持可回退版本，尤其不要直接编辑线上文件。 |

数据量增长后，定期看磁盘和备份大小：浏览器 profile、日志和多份备份远比几个 JSON 文件容易占空间。当前 14 GiB 余量尚不要求立即扩容，但应先排查增长来源，不随意删账户 profile。

## 扩容与维护的触发条件

初期可用以下**建议阈值**做判断，需随实际使用修订：普通本地 API 的 p95 持续超过 1 秒、频繁出现 Waitress 队列告警；可用内存反复低于 300 MiB 并伴随持续 swap in/out；出现 OOM；磁盘超过 80%；或智慧树一轮刷新耗时逼近设定的刷新周期。

先确认是上游慢、浏览器还是本地数据处理，再决定动作。内存紧张时优先错开认证、降低同时浏览器数，或升到更大内存；上游慢时继续把同步移出请求路径并加全局并发上限。**不能直接把 Web 服务改成多进程**：JSON 锁和登录启动锁是进程内锁；智慧树已有独立 worker，不代表多份 Web 进程可安全写同一份数据。

有跨用户共享/协作需求，或确实需要多个写进程时，再考虑数据库和跨进程协调。文件拆分能降低修改耦合，但不会自动提升服务器容量。

## 更新日志要做多大

现在需要一个轻量记录，不需要公告后台、弹窗强制已读或通知系统。仓库用 `CHANGELOG.md`，站内在上手指南底部放简短「最近更新」。只写同学会感知的变化：新增入口、行为调整、已修复问题、是否需要重新下载 Agent 包；实际部署时才填写发布日期。两处说明在同一次提交更新。

## 发布前验收

1. `/welcome`：桌面和手机的登录／注册展示清楚，隐私说明可打开。
2. `/preview-login`：进入独立示例账户，总览刷新无逐卡片闪烁；已有布局保留。
3. 左侧「上手指南」：目录可跳转、长内容可滚动；Canvas 日历馈送截图可加载；手机菜单可进入。
4. 待办新增、完成、平台子任务、项目下一步、日程关联与重复单次完成保持原行为；Canvas 完整日期与其他来源一致。
5. 完成自动化验收后，由产品维护者确认实际效果；再按现有规范合并、推送、备份和部署。当前文档不等于已上线或已验证真实平台登录。
