# Canvas Dashboard 产品优化建议

审阅日期：2026-09-26。依据当前代码、开发文档及 normal / dense 隔离预览。UI 提案见同目录 `ui-optimization-2026-09-26.html`。本次交付是建议与原型，没有改动应用行为。

当前最值得投入的方向，是降低“把事情收进来之后，判断现在做什么”的成本。已有的平台聚合、统一事项、项目、排程和日历能力比较完整，暂时不建议再扩大首页模块数量。以下是基于代码和示例场景的判断，尚无真实使用数据支撑收益量化。

## 1. 优先让日期与数量的含义更清楚

当前底层已经区分计划日期和真实截止，但清单上的日期胶囊容易被理解成同一种日期。建议在显示上明确写“计划今天”“今天截止”“未设日期”，详情和日历沿用同一口径。不要给未核实的截止自动补日期。

首页待办计数、项目行动和日程有不同含义。建议给摘要加简短口径说明，能从数字直接进入对应结果；例如“今天截止”只统计真实截止，不把今天安排的项目练习计入。重复待办仍按现有规则展示最早未完成的一次，在详情解释“还有后续次数”，避免用户以为只生成了一次。

验收：同一项目行动同时出现在待办与日程时不重复计数；计划但无截止的行动不会被显示成逾期作业；重复系列完成旧次后，用户能理解为何出现下一次。

## 2. 把数据可信度放在用户需要判断的地方

产品已经有连接与同步页面、平台状态元数据和同步提醒。建议完善其表达：区分“已连接”“最近成功更新”“正在更新”“保留旧结果但本次失败”，并明确哪个平台受影响。“连接正常”不等于“数据刚刚更新”。

首页只展示简短摘要和必要异常，点开看到逐平台更新时间、错误原因和下一步操作。不要让一次同步失败把有价值的旧任务清空，也不要把从未连接的平台算成同步故障。此建议沿用现有元数据与缓存机制，不另造一套状态存储。

验收：一个平台过期、另一个平台正常时，任务继续可见，异常定位到具体平台；断网时清楚说明“显示上次成功结果”；首次未连接与同步失败使用不同空态。

## 3. 缩短“记下”和“找回”的路径

手机常规预览中，新增表单高约 225 px，第一条待办从页面 y ≈ 693 px 开始。建议把新增入口改成标题旁按钮，打开后先填标题，日期、重复与更多字段按需填写。用户主动创建时保留清晰的字段说明，不能用模糊的自动日期解析替代确认。

现有“查找事项”入口在今日日程底部。建议把同一个搜索能力提升到工作区顶部或固定入口，并提供可发现的键盘快捷键说明；复用现有搜索与统一详情，避免形成第二套检索结果。

验收：手机打开首页能直接浏览任务；新增后回到原位置；找一条无日期或历史计划事项不需要先滚到日程底部。

## 4. 完成操作提供就地反馈，删除保持明确

统一详情已经支持重新开启事项、撤销本次完成等操作。建议在清单完成后增加短反馈和“撤销完成”入口，减少误点后的找回成本；仅在请求成功后确认状态，或在乐观更新失败时恢复原项并说明原因。

项目删除目前是永久删除，不能在界面上暗示可恢复。删除前展示具体对象与后果。遇到版本冲突，保留用户尚未保存的文字，提供重新加载或复制草稿的路径，避免只显示错误后丢失输入。

验收：撤销完成后同一事项在待办、项目与议程中的状态一致；保存失败不丢草稿；冲突时不静默覆盖其他端的更新。

## 5. 长期项目强调“当前一步”，而不是增加进度仪表

已有唯一主项目和 Next Action 的模型非常适合个人使用。建议首页只突出主项目的当前一步，其他项目缩成摘要；完整目标、资料、后续候选步骤继续在项目详情中查看。没有可靠总工作量时，不增加任务数百分比或“项目进度条”。

完成一步后可以提供“查看项目”入口，由用户决定下一步。不要自动生成复盘、自动填满今天或把候选步骤批量变成待办。暂放项目可在项目页找回，不占用首页注意力。

验收：主项目一眼可辨；详情仍能查看全部项目与资料；完成一步不自动生成未授权的任务链。

## 6. 首次使用先完成一条可理解的链路

建议在首次未连接时给两条简洁入口：“连接一个常用平台”和“先添加待办”。选平台后解释接入方式与能读取什么；日历订阅、Agent 接入等功能在使用需要出现时引导，不把所有设置同时展示成新手任务。

验收：用户能完成“连接 / 添加 → 看到一条事项 → 查看截止 → 标记完成”的闭环；暂不连接任何平台也能使用自定义待办；所有引导可以跳过。

## 工程与维护建议

- **先解决文档中的实际矛盾。** `docs/development.md` 的 Agent 写入说明仍写着“普通待办暂无自动续期，recurring 仅为每周时间安排，不支持隔周规则或生成下次待办”，与当前 `recurring_todo_store.py`、AGENTS.md 中的原生每周 / 隔周待办能力不一致。应区分日程 recurring 与原生重复待办后同步说明，避免后续维护按旧规则设计。此次仅记录问题，没有擅自改写规范。
- **沿现有组件层收敛样式。** 已有 Token 与组件系统，不必更换框架。后续视觉实现避免继续向 legacy 样式追加覆盖；逐个业务块迁移并验证，不进行全量样式重写。
- **再拆分时以变更频率为依据。** `frontend/templates/index.html` 仍承载大量业务脚本，已有 `features/` 可承接逐步迁移。优先迁出本次实际改动的逻辑，并复用 API client 与统一详情；不为本次设计提案做无关重构。
- **字体可用性作为体验检查。** 当前通过 Google Fonts 加载 Geist 与 Noto Serif SC。建议检查弱网和字体加载失败时的布局；若以后考虑本地托管，先核对许可证、字体体积与中文子集策略。本提案直接使用系统回退字体，离线可看。

## 推荐顺序

1. 第一轮：手机新增表单、待办来源去重、计划与截止标注、无日期占位、完成反馈。
2. 第二轮：按选定视觉方向调整顶部摘要、字体层级、主项目与日程；提升已有搜索入口。
3. 第三轮：首次使用、同步异常、保存冲突等完整状态，并核对对应文档。

每轮都可独立验收。UI 在真实应用中落地后，再运行受影响测试与 `scripts/test.ps1 -Suite acceptance`，并检查 normal / dense / empty 场景。独立 HTML 的浏览器检查只证明方案页可用，不证明生产业务或第三方集成通过验收。
